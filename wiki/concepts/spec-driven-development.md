Spec-Driven Development (SDD) is a 2025-2026 software methodology where versioned, structured specifications — not code — are the primary artifact and source of truth. Code is generated or maintained against those specs by humans and AI agents.

## Core Workflow (4 Phases)

1. **Specify** — author a spec with user stories, EARS acceptance criteria, and constraints
2. **Plan** — translate spec into a technical plan (architecture, data model, API contracts)
3. **Tasks** — decompose the plan into atomic, independently-shippable tasks
4. **Implement** — execute tasks with verification against acceptance criteria

## Three Levels

- **Spec-first** — write a spec for a single task, discard after implementation
- **Spec-anchored** — maintain spec alongside code; edit spec before touching code
- **Spec-as-source** — only humans edit specs; code is a generated byproduct

## Tools

GitHub Spec Kit, AWS Kiro, Claude Code (cc-sdd skills), Cursor Plan Mode, OpenSpec, BMAD-METHOD, Tessl, Google Antigravity.

## Relationship to Other Practices

SDD vs TDD: TDD treats a failing test as primary artifact; SDD treats the spec as primary. SDD vs Vibe Coding: vibe coding is fast for prototypes, SDD is disciplined for production. SDD is not waterfall — specs are living, version-controlled artifacts in the same repo as code.
